# 技术规划

技术选择发生在实际应用架构工作中，不是角色安装或 CLI 初始化选项。第一次应用架构工作，以及之后受影响范围缺少足够技术说明时，使用本流程。快速迭代可以缩短文档，但仍交付可用技术目录（catalog）和每个受影响前端/后端范围的子档案（child profile）。没有应用技术选择的纯文档、可行性、数据或集成任务不强做前后端档案。

## 真实产物与位置

先查用户业务目录和项目已有约定。已有 catalog/child 等价文档可直接维护，不必改名搬家；不能只列一张目录表却不读取、补齐其受影响子档案。文档可用意味着它是实际项目成果，已填写本次相关内容、引用来源，具有 `Proposed` 或 `Confirmed` 状态，足够支撑本次工作；原封不动的模板不算成果。遇到 `Superseded` 先沿替代链接找到当前版本。

无既有约定时，以下是相对**用户业务根目录**的可选默认位置，不是角色/Skill 安装路径：

| 产物 | 默认业务路径 | 完整模板 |
|---|---|---|
| 架构说明 | `docs/architecture.md` | [架构说明模板](../assets/templates/architecture.md) |
| 稳定技术目录 | `docs/technology-profile.md` | [技术目录模板](../assets/templates/technology-profile.md) |
| 每个受影响前端范围 | `docs/technology/frontend/<scope-id>.md` | [前端档案模板](../assets/templates/technology-profile-frontend.md) |
| 每个受影响后端范围 | `docs/technology/backend/<scope-id>.md` | [后端档案模板](../assets/templates/technology-profile-backend.md) |

项目已有 `docs/ai-sdlc/`、其他资料仓库或功能目录时优先沿用。由用户指定或已约定的成果仓库决定落盘位置，源代码仓库仅用于证据不意味着可写入。路径依据真实文档位置计算：例如上述默认目录中的前端子档案指向 catalog 的链接为 `../../technology-profile.md`，catalog 指向子档案为 `technology/frontend/web-app.md`。模板中的 `[文字](<占位路径>)` 必须替换成实际相对路径或权威 URL；不存在的成果不能登记为链接。

## 状态与决定约束

| 层级 | 状态 | 含义 |
|---|---|---|
| 文档 | `Proposed` | 已形成真实内容，仍有需要接受的选择 |
| 文档 | `Confirmed` | 文档已确认；仍可保留不阻塞本次工作的观察或未知项 |
| 文档 | `Superseded` | 已被替代，必须给出真实替代链接 |
| 条目 | `Observed` | 经证据核实的当前状态，不代表目标已接受 |
| 条目 | `Required` | 用户或项目已明确确认的要求，约束实施 |
| 条目 | `Proposed` | 推荐或待接受的目标选择，不约束实施 |
| 条目 | `Accepted` | 已被实际接受的选择，保留决定者与来源，约束实施 |
| 条目 | `Excluded` | 明确排除的方向或不适用范围，必要时解释理由 |
| 条目 | `Unknown` | 尚缺事实或决定，说明对本次工作的影响 |

只有 `Required` 和 `Accepted` 指导实施。`Confirmed` 文档不能掩盖当前实施所需的关键 `Proposed` 决定；关键事项未解决时暂停其依赖部分，其余继续。当前证据与目标要求/选择放不同列：若一项同时需要记录独立 `Observed` 证据及 `Accepted` 目标，可拆行明确，不用一个状态混指两件事。模板中的状态值保持一致，面向用户解释其中文含义。

## 首次应用与缺口补齐流程

1. **先找现有资料。** 查业务目录、现有索引和已配置只读来源中的 catalog、列出的 child profiles、实际接受的 ADR、契约、架构图及代码证据。逐条读取本次受影响范围的子档案，沿替代链接找当前文档。可直接读取的本地文件无需 host 或 bridge；跨 Git、固定版本、比较或导出确有需要时，按 [协作与交接](collaboration-and-handoff.md) 复用已有 bridge。不得为查资料强制初始化其他仓库、复制只读桥接成果或创建主机登记。
2. **识别真实仓库和部署范围。** 从代码结构、部署配置、现有文档和用户请求判断前端、后端或二者，以及每个应用、服务、worker、函数等实际部署单元。记录职责/使用者、真实仓库、证据路径/版本与负责人。仓库字段沿用现成标识及核实后的映射，或使用仓库名加规范 Git 远端/真实本地根目录；不要求 `.ai-sdlc/installation.json`、全局 `repositoryId`、CLI 初始化或预留身份。不同仓库必须可区分，同一仓库可以有多个范围，不能只按仓库名合并档案。只询问无法推断且影响本次决定的信息。
3. **确定安全范围标识。** 沿用已确认 Scope ID；新建文件需要标识时使用稳定小写 kebab-case 单段，匹配 `[a-z0-9]+(?:-[a-z0-9]+)*`。拒绝斜线、反斜线、点路径、百分号编码、仓库路径和 URL。Source host/path 是读取证据的位置，不是仓库身份；尚未存在的源写 `Planned / Not created` 并记录真实计划名称，不虚构主机/路径，创建后再补事实。实施者先匹配真实仓库及类型，再匹配本次部署单元或 Scope ID 集合，歧义未解决时不能混用约束。
4. **按关注点分类。** 每个范围标 `Existing`（现有）、`Greenfield`（新建）或 `Hybrid`（混合）。混合子档案中的保留项按现有流程，新建/替换项按新建流程，明确它们之间的共存、兼容和迁移边界。
5. **查现有证据再提出目标。** 现有部分检查依赖清单、锁文件、源码结构、部署/CI、API schema、迁移及项目规则，当前基线保持 `Observed`。现有技术满足已确认需要时优先保留；已有明确要求、实际接受的决定与授权直接沿用来源，不重办确认。推荐保留但尚未实际接受的实质目标先写 `Proposed`，在对话中请人接受基线一次，再将实际接受的目标改为 `Accepted`。实质变更单列目标，不能把检测到某依赖当作接受证据。
6. **新建部分从约束出发。** 先厘清产品、运行、治理、团队、生态、托管、兼容与交付约束，再命名工具。每个实质选择通常比较两到三个真实可行候选，推荐在前并说明一句取舍；只有一个可行时说明排除其他方向的证据，不凑候选数。实际人类接受前保持 `Proposed`，接受后记录选择、决定者及来源，并改为 `Accepted`。
7. **在理解约束后处理偏好。** 只询问影响本次选择的未知栈偏好；偏好是上下文，只有用户明确确认为要求时才标 `Required`。需决定时在当前对话使用可用且适用的提问方式，不把问题埋在文档，也不将沉默、推荐或未回复当接受。已有答案直接沿用。
8. **读取完整模板并写成实际成果。** 没有可用 catalog 就从 [技术目录模板](../assets/templates/technology-profile.md) 创建，已有则补充本次范围；仅为受影响前端/后端读取 [前端模板](../assets/templates/technology-profile-frontend.md) 或 [后端模板](../assets/templates/technology-profile-backend.md)，建立或更新实际子档案。保留本次适用的专业字段和技术关注点，来源、现状/目标、状态与取舍必须可用；不因 rapid 而只交一句“沿用技术栈”，也不填无关空格或为无关部署单元建档。
9. **共享决定只维护一处。** API/事件契约、身份与认证、授权/信任边界、兼容/版本、跨范围部署或迁移顺序、排除方向及 ADR 放在 catalog 或共享架构说明中的一个权威位置。子档案只链接它，不能重新定义一份。范围专属框架、构建、状态、数据访问和测试选择保留在对应子档案。
10. **保留必要决定并完成交接。** 持久、跨仓、迁移、难逆选择或架构规则例外使用 [ADR 模板](../assets/templates/architecture-adr.md)，记录证据、实际考虑的选项、代价、未来规则和验证/重评触发。按实际需要更新架构说明、C4、模式、质量或风险资料。核对 catalog 与 child 双向链接、范围和状态，维护已有业务索引，仅列真实文件，交付路径、依据版本、已检查项及尚缺决定。

## 专业覆盖

完整字段及技术行直接保留在模板中。先读相关模板再落盘；只处理适用领域，容易被误认为漏项的排除显式标 `Excluded` 并说明依据。

- **前端：** 语言/运行时/版本、包管理/工作区、构建/打包/开发服务、框架/渲染、路由、组件/设计系统、token/样式/主题/素材、布局/响应式、本地/全局/服务端状态及缓存失效、表单、API 行为、会话、适用客户端安全/隐私、无障碍、国际化、浏览器兼容、性能、可观测性、测试、托管/CDN/环境。
- **后端：** 语言/运行时/框架/构建、服务/模块/领域/部署边界与拆分理由、API/契约行为、集成与消息、事务/并发、作业、数据归属/schema/存储/查询、迁移与回退、认证/授权/租户/服务身份/秘密、隐私/审计、可观测性、健康/韧性/容量和测试。

先描述要求再写产品名。不得为规划添加并不存在的服务、层、供应商、平台能力或部署范围。技术目录不依赖 PM、Designer、Engineer、Tester 或 DevOps 角色安装；技术规划也不授权安装依赖、脚手架、改业务代码/数据库结构/生产配置或执行迁移。

## 后续更新与交接

需求迭代先列受影响范围及原结论依据，复核其现状、目标、决定和共享依赖，只改本次受影响 catalog 行、child profiles 与关联产物。已接受且仍适用内容沿用；被替代内容标 `Superseded` 并链接替代文件，不能让旧结果冒充当前验证。

落盘前核对：每个受影响范围均能定位真实仓库及部署单元，catalog 指向实际 child，child 回链正确，所有必需实施决定已解决或明确阻塞，共享规则没有重复冲突，来源及版本足以追溯，模板占位链接已替换。无法执行的验证如实列出，不宣称已实施或迁移。交接交代实际文件、使用范围、必需约束、已接受/未决事项、兼容迁移影响、验证方法和仍需证据；索引仅使用现有业务机制，不强建安装登记外壳。
