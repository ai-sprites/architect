# 决定与取舍

系统边界、共享契约、跨范围协调、迁移、持久/难逆的架构决定与规则例外使用本流程。记录足以指导实现的真实约束；具体语言、框架、库和构建工具由开发角色选择，不要求先有架构师的选型档案。

## 从问题到架构决定

1. 写清架构问题与必须保持的用户行为，不在问题里预埋技术答案。核实四层上下文：业务结果、压力、负责人或衡量方式；产品用户、旅程、渠道和范围；工程现状、集成、数据归属、团队和运行限制；真实法规或政策。每项保留来源、架构影响和信息缺口，没有证据就不编造。
2. 找已有架构/技术说明、实际接受的 ADR、契约及相关代码。明确受影响部署单元、职责/使用者、所属仓库、真实来源路径/版本与负责人；同一仓库可能有多个前后端范围，不能只按仓库名合并互相冲突的约束。未建仓库标明计划/尚未创建，不能虚构主机或路径；已有过时说明沿替代链接找到当前版本。用于文件名的标识必须是安全单段，不得含斜线、反斜线、点路径、编码逃逸或直接使用仓库路径/URL。
3. 每个范围区分现有、新建或混合。现有部分检查清单、锁文件、源结构、部署/CI、契约、迁移和项目规则；混合部分将保留与新增/替换分别分析，写明兼容与迁移边界。观察当前状态与目标要求/选择分开；依赖名能证明当前使用，不能独自证明性能、团队熟练度或未来适用性。
4. 现有架构满足需求时沿用，已有实际接受的决定与授权不重复确认。发生实质架构选择时，先厘清产品、运行、治理、团队、生态、托管、兼容、预算和交付约束，再询问影响本次决定的未知偏好。偏好只有被明确确认为要求后才能约束方案。
5. 通常给两到三个真实可行方向，推荐在前，说明每个方向满足哪些约束、收益、实施/维护成本、风险、兼容/迁移及可逆性。只有一个可行方向就给排除其他方向的证据，不凑数量；无真实竞争方向的延续性小改动不强建比较文件。
6. 保持观察、明确要求、建议、已接受、排除、未知的区别；只有明确要求和实际接受的决定约束实现。项目用中文或已有状态词表都可以，但文档被称为已确认不能掩盖实施所依赖的未决建议。需用户决定时优先使用客户端已有且适用的结构化提问界面，否则在对话提问；有可行选项时给两到三个互斥选择、影响和有依据的推荐，推荐在前。缺失事实直接自然询问；只等依赖部分，答案后把选择、决定者与来源写回相关说明。
7. 按下面覆盖形成可用架构说明；共享契约、身份/信任边界、兼容规则、跨范围迁移/部署顺序与 ADR 保留单一权威来源，其余范围链接它。保留明确排除项的原因，不重复定义互相冲突的规则。
8. 验证当前交付是否足以实施：关键选择已决定或依赖部分明确受阻，现状/目标/约束与来源清楚，必要兼容和迁移有解释，验证方法与真实检查结果已列明。决定及评审产物保存在业务仓库 `docs/architect/`，旧散落产物迁入后保留用户内容并同步文档链接、已有索引和消费引用，目标冲突先比对合并。更新已有架构入口/索引，只登记真实文件、用途、当前/过时/无需状态及替代关系，不为此另建一整套管理目录。

## 每个受影响范围的专业覆盖

这些是审查提示，相关项必须处理；无关项可以省略，容易被误以为漏项的排除要解释理由。先写要求再写产品名，架构取舍与实际规模相称，不逐项替开发决定工具。

- **共同说明：** 范围/部署单元及职责或用户、所属仓库与真实来源、现有/新建/混合、当前证据、目标要求/选择、决定状态及来源/取舍，产品/交互/集成/数据约束、实际运行与团队限制，共享契约/身份/兼容/ADR 链接。待决事项保留为何现在需要、受影响范围、可行选项、推荐及需要人回答的具体问题；被替代说明指向替代版本。
- **前端边界与质量：** 应用与设计系统边界，影响系统结构的渲染与部署要求，客户端/服务端状态归属及缓存一致性，共享契约、会话与信任，安全隐私、无障碍、兼容和性能目标。具体框架、组件、状态管理、样式及测试工具由开发角色落实。
- **后端结构与集成：** 服务/模块/领域/部署边界与拆分理由；实际协议/资源/方法/版本、权威契约所有权与生成、状态/错误/分页/幂等，集成协议，超时/重试/熔断/降级，消息/事件/交付语义，作业/调度/取消。
- **后端数据：** 领域模型、事务、并发，记录源与归属、schema、规范化/一致性，查询及缓存/搜索/对象存储的边界与一致性要求，数据库迁移及先扩展再收缩、部署顺序/回滚/备份/恢复。
- **后端安全与运行：** 认证，授权角色/策略/资源/租户边界，服务身份/秘密，加密/隐私/保留/审计；日志/指标/追踪/关联/脱敏；健康/就绪/伸缩/韧性/容量；单元/服务/集成/契约/迁移/安全测试。

新设计的项目自有前后端 HTTP API 默认采用 RESTful 资源/一致 URI 和方法、正确 HTTP 状态、统一且文档化的 JSON 包装及适用例外、明确分页方式和边界、一份权威 OpenAPI YAML 并在行为变更时同步更新与检查。既有项目已确认协议/格式及用户指定规范优先，不因引入实践迁移已有 API；非 HTTP 或第三方接口不套此默认。实质偏离或兼容例外必须记录范围、取舍和迁移影响。

架构说明保留当前证据、已确认约束、重要取舍及其实施影响，沿用已有文档即可；开发者自己的具体选型无需经过本流程或另建技术档案。

## 方案与决定记录

真实竞争方案比较保留问题、上下文、决策驱动的重要性与证据/假设；每个方案的核心想法、适配驱动、成本风险、迁移/兼容；共同比较收益、成本、满足约束和可逆性。推荐要说明依据，与实际选定答案分开；没有真实选择不能填写选定人或日期。

持久、跨仓、迁移、难以撤回选择或项目架构规则例外必须有可引用记录。沿用项目 ADR 或已有架构文档短节，以下已知内容必须保留，未知内容注明其影响：

- 实际选择、决定依据与涉及范围，区分建议和已接受约束。决定人、日期和稳定标识只在已知且影响交接时记录，普通选择不逐条建档。
- 触发决定的上下文、现实约束及证据，一项清晰可执行的决定。
- 实际考虑的方案、各自能成立的理由及未选理由；正面结果，以及成本、风险、迁移或运营负担。
- 未来工作必须保持的规则、不得采用的选择，适用范围和项目规则的例外边界。
- 可重复的验证或证据、何时需要重评，后续检查和尚未解决的风险/负责人。

涉及迁移时明确现在与目标：保留、替换、共存方式、迁移期间的权威数据/契约来源、分阶段部署与回退、破坏性变化及影响。沿用已接受的决定；实质新决定不能在未接受时当实施命令。快迭代不会降低安全、隐私、数据损失或难逆选择的决策与验证标准。

例如应用增加导出任务，应先核对任务量、完成时限和现有后台能力。现有机制满足需求则复用；确有隔离或容量要求再比较独立执行器，不能无任务量证据就选择消息平台。

延伸阅读：[ADR 社区说明](https://adr.github.io/)。它解释如何保留决定缘由，不要求固定模板、状态英文词或目录。
