# 决定与取舍

先写清触发选择的现实问题和必须保留的行为。已有技术满足需求时直接沿用；依赖名能证明当前用了什么，不能独自证明性能、团队熟练度或未来适用性。

比较实际可行的方向即可，不为了表格而凑满选项。对每个方向核对：当前限制能否满足、实现与维护成本、与已有系统的兼容、失效后如何退出。团队经验、预算、部署环境和政策只使用已知事实；缺少的关键约束进入“待确定”。

涉及迁移时，将现在与目标分开：哪些组件保留、哪些替换、两者如何共存、迁移期间谁是权威来源。一个新库或服务应减少当前问题，而不是把问题变成更多需要运营的组件。

若选择需要留痕，可用一个短段落或沿用项目 ADR：为什么现在需要决定、选择什么、依据来自哪里、有哪些成本、如何验证以及什么变化会让它需要重评。建议写为建议，已有决定链接其证据；不为未发生的批准填写人名和日期。

例如已有应用需要增加导出任务，先核对任务量、完成时限和当前后台能力。现有任务机制满足条件时复用；确有隔离或容量要求再比较独立执行器。没有任务量证据时不靠想象选择消息平台。

延伸阅读：[ADR 社区说明](https://adr.github.io/)。它帮助保留决定缘由，不要求采用固定模板、状态系统或目录。
