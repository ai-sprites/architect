# 边界与验证

系统关系、边界变化、质量目标和架构风险使用本流程。先核实系统，再解释本次变化；相关专业内容必须完成，文档数量与真实问题相称。

## 分析顺序

1. 从实际请求或数据流识别调用者、被调用者、数据归属与信任边界，核实模块、应用、服务、存储和外部系统。分清代码职责、独立部署和授权隔离，不把目录直接当成独立服务。
2. 记录现状、需要改变的边界、原因和受影响对象，链接实际来源/版本、已有接受的决定、项目规则、兼容约束和质量目标。只变更受影响范围，保留仍适用结论。
3. 检查本次相关的 API、数据、集成、安全、可观测性、前端、运行和验证；每项说明是否适用、当前决定或缺口及证据。共享 API/事件契约、身份与信任边界、兼容及协调顺序保留一个权威来源，各范围链接而不重复维护。
4. 拆分要能解释现实收益与成本：跨进程通信、失败处理、部署协调和运行信号。只有当前隔离、独立发布、容量或归属需求值得承担时才新增服务/层/平台；可用模块解决就不提前拆服务。
5. 实质系统/部署边界变化更新相应 C4 视图；记录已确认质量目标和真实重要失败场景；执行项目适用图/契约/迁移/安全/性能检查，并区分已检查和未验证内容。
6. 交付可实施说明：问题/范围、当前方向、约束、各关注点决定/缺口/证据、共享来源、有效决定与状态/范围、公开风险的影响/负责人/所需证据/后续检查。已存在入口或产物索引随变更更新，只列真实存在的内容和用途/时效状态。

## 相关架构关注点

- **API：** 契约归属、实际资源或操作和版本、状态/错误、包装与例外、分页、机器契约与检查；新设计的项目自有前后端 HTTP API 默认采用 RESTful 资源/URI/方法、正确 HTTP 状态、统一文档化 JSON 包装及例外、明确分页、一份权威 OpenAPI YAML 同步更新并检查。既有已确认协议/格式或用户指定规范优先，不因实践接入迁移既有 API；非 HTTP/第三方不套此默认。偏离或兼容例外记录范围、取舍与迁移影响。
- **数据：** 系统记录源、写入与事务边界、归属、schema/迁移、并发/一致性、缓存和保留；明确数据损失影响及所需恢复证据。
- **集成：** 同步/异步、超时、重试、幂等、失败处理、契约翻译、消息交付语义及相关恢复路径。
- **安全：** 身份传播、服务端授权、资源/租户与信任边界、秘密和敏感数据处理；只使用已知安全分类、治理/监管约束，不凭空宣称合规。
- **可观测性：** 结构化日志、指标、适用追踪、关联标识、脱敏与可见失败信号。
- **前端：** 框架/渲染、路由、状态归属、服务端数据/缓存、设计系统边界和兼容。
- **运行：** 部署/托管/环境、伸缩、韧性、健康/就绪、容量、迁移/回退与备份恢复。
- **验证：** 相关契约、行为、迁移、安全、性能及恢复证据，检查方法、适用条件、失败信号与尚未验证项。

已有项目规则需要改变或设例外时，先核对规则来源与适用范围，以证据和可引用决定解释选择、取舍和迁移影响；不得因插件示例或个人偏好新增全项目规则。活跃实现模式保留关注点、位置、适配理由、代价和证据/执行方式；被拒绝或替代模式保留曾考虑理由、拒绝/替代理由及有关决定，不把失效规则继续交给实现方。

## C4 与图的验证

- 系统上下文图（L1）只包含真实用户/人物、目标系统、外部系统、各自职责及业务关系；不塞入容器、存储或部署细节。
- 容器图（L2）说明目标系统边界内实际应用、服务、存储、队列的职责与技术，必要时带入能解释关系的人和外部系统。关系写明真实业务用途、调用/读写方向及协议；不要把副本、负载均衡器或部署节点混进容器图。
- 只画已确认对象与关系，未知关系放图外的待确定项，记录来源和影响。保留真实名称或稳定标识，支持决定与质量目标引用有关元素。
- 使用项目已有绘图语法。存在项目 Mermaid/图检查就运行，并实际核对可渲染性；没有检查或无法运行时记录实际采用的检查与限制。语法能过不代表边界事实已验证。

## 质量目标

质量目标必须来自已确认需求或决定，不为填表捏造数字。响应时间说明负载与统计条件，可用性说明时间窗口及故障范围，恢复说明可接受数据损失和恢复时长；无数值时保留缺口、影响和测量方式，不能擅设目标。

每个适用目标保留稳定标识、质量属性（如延迟/可用性/容量/安全/恢复）、负责的图元素或系统关系、已确认目标/二元门槛、窗口与条件、可重复检查方法、来源/证据、可观察失败信号。目标决定记录实际选定目标、决定者与来源。存在多个需独立维护目标时单独成文，否则可合入架构说明。

## 风险评审与后续验证

用“触发条件 → 失败位置 → 用户/业务影响 → 应对与验证”分析本次真实风险。至少检视与当前改动实际相关的峰值负载变化、恶意输入/权限突破、关键依赖不可用、并发、数据损坏或丢失；不为所有理论风险造场景或系统。

每项重要风险保留场景、触发条件、失败元素/位置、可见影响、应对或已接受风险、负责人、相关 ADR/目标/规则；区分事实证据与未知项，说明所需日志/指标/检查、必要改动、后续验证和受影响产物。没有被实际接受的风险不能写成“已接受”。多项重要失败场景需要集中评审时形成单独风险说明，其余可留在对应决定或架构说明。

快迭代不降低安全、隐私、数据损失或难逆决定的标准：关键未知只暂停依赖部分，提问或取得所需证据后再完成该部分，其余继续；不能用“之后检查”冒充已验证，也不能以项目规模小为由省掉已知实质风险。
