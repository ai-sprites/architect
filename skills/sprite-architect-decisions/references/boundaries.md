# 边界与验证

从实际请求或数据流画出调用方、被调用方与数据归属。先核实模块、应用、服务、存储和外部系统，随后判断需要解释的是代码分工、独立部署还是信任边界；不要把目录直接当成独立服务。

每次拆分都有成本：跨进程通信、失败处理、部署协调和运行信号。当前已有明确的隔离、独立发布、容量或归属需求才值得承担这些成本；可以用模块解决的问题无需提前拆服务。

需要图时，C4 的系统上下文解释用户、系统和外部关系；容器视图解释应用、服务与数据存储。只画已确认对象，关系注明真实用途与协议，未知关系写在图外的“待确定”清单。复用项目已有绘图语法并实际验证可渲染性；不用图更清楚时直接写文字。

质量约束从真实目标出发。响应时间需要负载与统计条件，可用性需要时间窗口和故障范围，恢复需要可接受数据损失与恢复时长。没有已确定数值时记录缺口或提出测量方法，不自填目标。

风险用“触发条件 → 失败位置 → 用户或业务影响 → 应对与验证”描述。针对本次相关的依赖不可用、并发、数据损坏、权限边界或负载变化检视即可；无需为每个理论风险新建系统。说明观察失败需要什么日志、指标或检查，记录实际证据和仍未验证的部分。
