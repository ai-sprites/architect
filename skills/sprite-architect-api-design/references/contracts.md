# 契约内容

新增或细化契约时依次完成以下工作，修改接口还需结合 [兼容与演进](compatibility.md)。沿用项目真实协议与权威契约；既有项目已确认协议/格式和用户指定规范优先。新设计的项目自有前后端 HTTP API 使用下述默认专业规范，不因接入实践迁移已有 API。

## 确认来源与行为

先找调用者要完成的已确认动作、提供者/消费者、资源和数据归属、现有契约负责人及真实来源/版本。说明实际输入、输出、同步结果或受理后的异步结果，以及写入、通知等副作用；契约不能虚构后端能力或改变已确认产品行为。

新设计的项目自有前后端 HTTP API 默认按资源建模，使用一致 URI 和 HTTP 方法，前后端通信保留明确 RESTful 契约与资源/版本规则。已有已确认的 RPC、事件、内部接口、HTTP 格式或用户明确指定规范优先；非 HTTP 和第三方接口不套自有 HTTP 默认。实质偏离或兼容例外必须说明范围、理由、取舍和迁移影响并留下可引用决定，不借此擅改现有系统。

## 字段、权限与结果

- 输入输出核对类型、必填/缺失/默认/空值、长度与范围、单位、时区、标识含义、校验条件和示例；只列本接口真实相关字段。前后端若独立发布，字段行为必须可被双方一致理解。
- 身份认证回答调用者是谁，授权回答能对哪个资源做什么。写清身份/服务身份如何传递、资源/租户标识来源、哪里执行服务端授权、角色/策略与信任边界；客户端提交归属不能自动证明权限。
- 区分成功、业务拒绝、输入错误、权限问题和系统失败，定义稳定机器可识别语义及调用者如何恢复；面向用户提示与内部诊断分开，关联标识可以帮助追踪但不能泄露秘密或敏感数据。
- HTTP 接口检查资源/方法与状态语义，适当使用 `2xx`、`4xx`、`5xx` 表达传输结果；不能新设计“失败返回 200、只靠 body 标志”的约定。已有兼容性例外先核对消费者，以有范围和迁移影响的决定记录处理，不擅改现有系统。
- 新设计的项目自有 HTTP API 默认采用统一且文档化的 JSON 包装族，明确成功数据、稳定领域错误码/消息、可选详情、元信息和关联字段，同时保留 HTTP 状态语义。无正文、文件、流、健康检查、webhook 或第三方响应明确其适用例外，不塞进统一 JSON；已有已确认包装/格式或用户指定规范优先，偏离默认或兼容例外保留决定与影响。
- 异步受理说明任务/操作标识、后续结果或失败如何获得，以及真正完成的条件；流、文件、事件按实际交付语义说明。重试有副作用时写清重复请求处理，不能只说“可重试”。
- 分页接口必须明确游标或偏移、limit、排序、筛选、边界及无效/过期游标行为；具体选择和兼容检查见 [兼容与演进](compatibility.md)，未分页接口不自动引入分页。

## 权威契约与验证交付

接口设计、独立契约文档、决定、验证报告和附件统一保存在业务仓库 `docs/architect/`，新建独立 OpenAPI YAML 可用 `docs/architect/<feature-id>/openapi.yaml`。旧散落文档产物在本次更新时迁入该目录，保留用户内容并同步链接、已有索引和消费引用，目标冲突先比对合并。纳入编译、代码生成或测试的源文件按项目正常代码路径维护，不能复制第二份权威契约；来源读取不受目录限制。

保留一份项目认可的契约来源及负责人。新设计的项目自有 HTTP API 默认创建/维护一份权威 OpenAPI YAML，同步路径、方法、参数、请求/响应 schema、状态和示例，并运行项目 OpenAPI lint/契约检查。既有已确认的 OpenAPI、类型定义、RPC 描述、事件 schema 或用户指定规范优先，更新真实来源与示例并运行适用现有检查，不维护第二份会漂移的契约；实质偏离默认或兼容例外保留理由和迁移影响。

默认自有 HTTP 规范不适用且没有机器契约时，交付消除具体歧义的文字约定和可运行用例；不能以此跳过新设计自有 HTTP API 所需的权威契约。适用契约与示例在同次接口设计变更中保持一致；若已授权的任务还包括接口实现，行为和契约也必须同步，但接口设计本身不授权实现服务。

交付至少包括适用范围、来源/版本/负责人、提供者与消费者、操作及字段、权限/数据边界、成功失败和恢复、副作用/同步异步/幂等、适用分页、兼容与部署/迁移顺序、真实例子、运行的检查与结果、未运行项及未知语义的来源/影响/后续确认。共享约定链接权威来源，不能分散重复定义；过时契约标明替代版本。

持久、跨仓、迁移、难逆选择或已有规则例外保留可引用决定：实际答案与来源、范围/关联规则、上下文、替代方案及取舍、正负后果、未来必须遵守/避免的约束、验证和重评条件。决定人和日期只在已知且影响交接时记录，不为普通选择逐条建档。已有答案沿用；新的关键选择用客户端现成适用的结构化提问界面（无则对话），提供真实可行的两到三个互斥选项及影响、有依据的推荐在前，收到答案后再做依赖部分并写回决定。

安全、隐私、数据损失和难逆选择的约束不因快迭代降低；记录真实风险的触发、影响、证据/未知、负责人和后续检查，不用假想风险凑清单。

延伸阅读：[HTTP 语义](https://www.rfc-editor.org/rfc/rfc9110.html)、[OpenAPI 官方规范](https://spec.openapis.org/oas/latest.html)。仅在对应协议或工具适用时参考，并核对项目实际版本。
